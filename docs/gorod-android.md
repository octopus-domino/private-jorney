# Городской портал на Android

В 1.0.12 основной способ сопоставления в Петербурге — адресованный контур OSM, содержащий клик. Разбираются замкнутые ways и
полные multipolygon relations с несколькими внешними кольцами, внутренними дворами и фрагментами обратного направления.
Незамкнутые или неполные отношения не превращаются в заполненный прямоугольник. Двор и перекрывающиеся адресованные контуры
не разрешаются выбором ближайшего здания. Для подтверждённого контура проверяются адрес, корпус/литера и положение опорной точки портала;
порог 60 м от клика к центру не применяется к длинному зданию. Сам клик проверяется по настоящему контуру с вычитанием дворов.
Опорная точка портала после проверки точного адреса может быть в центре двора или выемки здания: для неё проверяется внешний
прямоугольник контура с допуском 2 м. Этот вспомогательный прямоугольник никогда не используется для назначения дома по клику.

Проверка живых данных: Славы, 30к1 — way 23201879 соответствует ID 44858 (литера А, МКД, паспорт опубликован),
отдельная служебная постройка way 540182528 — ID 28583 (литера Б, нежилое, паспорт на актуализации).
Данные одного не подставляются за другое. Успешные паспорта дополнительно кешируются по `facility:{id}`, чтобы разные части дома
использовали одну запись. Координатный кеш переведён на v2, чтобы не использовать ранее ошибочно сопоставленные точки.

Только при открытии карточки читается небольшой bbox через `https://api.openstreetmap.org/api/0.6/map`; подборки POI остаются исключительно CoDoc.
Кеш содержит только ID контуров, адреса и геометрию: сутки, до 12 областей. Уже полученный длинный контур используется даже за границей
первоначального bbox. Связь OSM-контура с ID портала также кешируется на сутки. XML с метаданными редакторов не сохраняется в приложении.
На Android endpoint разрешён только для GET маленького конечного bbox и работает в очереди домов; в dev разрешён помощником Vite.
Ожидание геометрии ограничено 10 секундами; недоступность источника оставляет прежний поиск по координатам/адресу как запасной путь.
Контракт чтения: [OSM API v0.6](https://wiki.openstreetmap.org/wiki/API_v0.6#Retrieving_map_data_by_bounding_box:_GET_/api/0.6/map).

Московская карточка использует собственные Polygon/MultiPolygon официального адресного реестра с внутренними кольцами.
Новый универсальный парсер OSM пока подключён только к сопоставлению петербургского технического паспорта; в других городах
наличие модуля не означает привязку всех карточек к контурам. Технические источники доступны только для двух столиц.

В 1.0.11 `.facility-no-tep` вместе с заголовком подтверждённого здания распознаётся как неопубликованный паспорт,
а текст об актуализации — как состояние `updating`. Пример из обращения: ID 139493, Мойка, 74, литера А, тип «Нежилое».
В карточке показываются подтверждённые сведения заголовка, сообщение источника, ссылка и повтор; отсутствующие числа не выдумываются.
Этот результат не сохраняется как полноценный паспорт и не запускает запрос `/programs/`. Неизвестный HTML, CAPTCHA или страница без
подтверждённого заголовка и маркера отсутствующего паспорта по-прежнему считаются ошибкой, а не успешным паспортом.

Версия 1.0.10 сначала определяет дом непосредственно через публичный `/public_api/maps/get_nearest/?latitude=...&longitude=...` городского портала.
Адрес и ID берутся из `buildings`, затем проверяются расстояние и неоднозначность; далёкий или неоднозначный результат не выбирается.
Проверка 18.11.2026: точка 59.9394057944393, 30.269812345504764 вернула ID 198090, «14-я линия В.О., дом 35, литера А»;
паспорт `/facilities/198090/info/` ответил 200 с `.facility-tep`. Photon для этого сценария не нужен.
Защищённый `/public_api/maps/get_building_by_coordinates/` вернул 401 и не используется.
Поиск по известному адресу и reverse-geocoding сохранены как запасные варианты. У Photon reverse установлен предел ожидания 10 секунд;
ошибки и зависшие запросы не сохраняются в кеш как успешный адрес.

Версия 1.0.8 уточняет диагностику в карточке: отдельно показываются сбой определения адреса, поиска в реестре и загрузки паспорта, HTTP-статус, сетевой сбой или тайм-аут. Ранее все исключения скрывались за сообщением «Городской портал временно недоступен», включая ошибки обработки ответа. Тела ответов и URL в диагностике не публикуются. Добавление диагностики само по себе не подтверждает устранение ошибки на конкретном телефоне.

В версии 1.0.7 запросы gorod.gov.spb.ru используют отдельную последовательную очередь WebView. Зависший запрос объявлений больше не задерживает поиск дома и загрузку его паспорта. Одна очередь на портал сохраняет ограничение нагрузки. При закрытии карточки отменяется только её запрос; при закрытии приложения освобождаются обе очереди.

Публичные запросы портала выполняются с настольным User-Agent и без cookies. Сессия мобильной версии сайта не нужна для чтения открытого паспорта. Настройки сессий остальных источников сохранены. Внешний сервер или обращение к localhost для этого не нужны.

Проверка реального сайта 18.11.2026: мобильный User-Agent получает 302 на `/m/#/facilities/36556/info/`, настольный получает 200 с `.facility-tep`. Мобильные Client Hints и X-Requested-With отдельно не вызвали перенаправления при настольном User-Agent. Это не доказывает причину ошибки на конкретном устройстве.

Также подтверждено: поиск `13-я линия Васильевского острова, 44` возвращает пустой массив, `13-я линия В.О., 44` возвращает дома. Подготовка запроса теперь заменяет полное название острова после слова «линия» официальным сокращением. Проверка координат и неоднозначности дома сохранена.

Ручная проверка живого источника: `node scripts/probe-gorod-browser.mjs`. Она проверяет реальный поиск и паспорт в Chromium с настройками запросов портала. Она не заменяет проверку установленного APK на Android. Проверка HTTP-перенаправления с разными заголовками: `python scripts/probe-gorod.py` (нужен curl_cffi).

Успешные паспорта по-прежнему сохраняются в локальном кеше; ошибки и отсутствие совпадений не сохраняются. Поиск мест интереса с codoc.site не менялся.
